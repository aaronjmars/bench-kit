# Bench standard v2.3 (bench-kit 0.4.0)

One shape for every bench repo: how runs are recorded, checked and reported,
whatever the bench measures (models, agent harnesses, prompts, CI runners,
forecasters).

This file is the source of truth. The JSON Schemas in `schema/` implement
sections 4 and 5; `bench-kit lint` implements section 9.

v2 revised v1 against how Harbor, Inspect AI / inspect_evals, SWE-bench,
tau2-bench, METR, OpenAI frontier-evals, HELM, lm-evaluation-harness, Every
Eval Ever, MLPerf, HAL, Epoch AI, BetterBench, ABC and Anthropic's error-bars
paper record results. v2.1 renames leaf fields to Every Eval Ever (EEE) 0.3.0
names wherever an equivalent exists, so `bench-kit export-eee` is a straight
mapping. v2.2 (bench-kit 0.3.0) adds optional clustered intervals
(`stats.cluster_by`), per-subject task and repeat counts
(`source_data.n_completed_by_subject`, `repeats.completed_by_subject`), an
optional `output` on sample rows for single_turn EEE export, and
significant-figure number formatting in generated files; every v2.1 manifest
stays valid and keeps `bench-manifest/1`. v2.3 (bench-kit 0.4.0) adds optional
per-metric task subsets (`metric_config.<id>.task_filter`,
`metric_parameters.field`, `metric_parameters.missing`), so a metric such as
recall over positive tasks or false alarms over clean controls is computed,
paired and linted by bench-kit instead of by each bench; a metric without them
works as before, and every v2.2 manifest stays valid as `bench-manifest/1`.
Sources at the end.

Note: every number, id and hash in the examples below is made up to show the
shape. They are not results.

## 0. Principles

1. **Standardize the record, not the runner.** Each bench keeps its code, runner
   and raw-data folders. The standard adds one manifest per run, one per-task
   file, and a fixed doc set. (Same split as SWE-bench/experiments: "entries,
   not artifacts".)
2. **One machine file per run is the source of truth.** Everything humans read
   (README latest block, RESULTS.md, runs index) is generated from it, so docs
   cannot drift. (inspect_evals generates its README report from logs.)
3. **Keep per-task results.** Totals alone cannot be re-checked, paired, or
   given error bars. Every framework studied keeps them.
4. **No number without its n and its uncertainty.** Verdicts follow the stats,
   not the other way round.
5. **Numbers are never edited.** Corrections are appended with who, when, why.

## 1. Files in every repo

| Path | Who writes it | What |
|---|---|---|
| `runs/<id>/manifest.json` | the run (or a human right after) | Source of truth for one run. Section 4. Required. |
| `runs/<id>/samples.jsonl` | the run | One row per task x subject x repeat. Section 5. Required when any metric is computed from samples. |
| `runs/<id>/` other files | the run | Raw logs, transcripts, judge outputs, as the bench already writes them. If not committed, `raw.location` or `raw.reason` says why. |
| `README.md` | human + generated block | Fixed sections, section 2. |
| `RESULTS.md` | **generated** | Every run, newest first, from manifests. Section 3. |
| `runs/INDEX.md` | **generated** | One line per run: id, date, question, verdict, status. |
| `METHOD.md` | human | Benchmark card + changelog + noise band + leak register. Section 6. |
| `NEXT.md` | human | Open work, known bugs, not-yet-run items, dated. |
| `CLAUDE.md` | human, optional | Agent-only operating notes and gotchas. |
| `docs/YYYY-MM-DD-<slug>.md` | human, optional | Long write-ups, linked from the manifest `writeup` field. |
| `.bench-lint-ignore` | human, optional | Repo-wide lint suppressions, one per line: `BL0xx <path glob> <reason>`. |

Run id = the directory name. New runs use `YYYY-MM-DD-<slug>`, unique per repo;
same-day reruns get `-2`, `-3`. Existing runs whose directory name is referenced
elsewhere (call logs, merged runs) keep their name; the date lives in
`started_at`.

Replaces ad-hoc FINDINGS / REPORT / SUMMARY / COMPARE / SCORECARD /
METHODOLOGY files (content moves into METHOD.md, manifests, or docs/).

## 3. RESULTS.md block (generated, newest first)

```
## 2026-01-15-summarizer-ab: baseline vs candidate

- Date: 2026-01-15. Question: Switch the summarizer step to the candidate model?
- Decision rule (set before run): SWITCH if diff >= +0.3 and CI excludes 0 and cost <= $1/run
- Compared: baseline (example-app@1a2b3c4 + example-org/model-a via provider-x); candidate (example-app@1a2b3c4 + example-org/model-b via provider-x)
- Tasks: example-tasks v2-A, 6 of 6 tasks x 3 repeats. Setup: standard. Judge: example-org/judge-model x1, prompt sha 1a2b3c
- Primary (report): baseline 3.20 [2.90, 3.50]; candidate 3.10 [2.80, 3.40]
- Comparison: candidate vs baseline on report: diff -0.10 [-0.35, 0.15], n=6 tasks, W/T/L 2/1/3 (sign test p=1)
- Errors: 0 of 36, counted as zero
- Cost: $2.40 total, api basis, prices as of 2026-01-15. Time: 30 min
- Verdict: KEEP. Status: complete
- Summary: candidate is cheaper but not better; keep baseline.
- Compared with: 2026-01-10-summarizer-ab (rubric changed, not directly comparable)
- Evidence: runs/2026-01-15-summarizer-ab/. Write-up: docs/2026-01-15-summarizer-ab.md
- Corrections: none
```

Numbers in generated files: values of 1 or more (and 0) use 3 decimals with
trailing zeros dropped (money 2 decimals); values below 1 use 3 significant
figures, so a cost of $0.00042 per task prints as `$0.00042`, never `$0.00`.

## 4. Manifest (`runs/<id>/manifest.json`, schema `bench-manifest/1`)

EEE names are used for: `eval_library`, `source_data.dataset_name`,
`model_info {id, name, developer, inference_platform}`, `generation_args`,
`llm_scoring {judges[].model_info, aggregation_method}`, `metric_config
{metric_name, metric_unit, evaluation_description, lower_is_better, score_type,
min_score, max_score, metric_parameters}`, `score_details {score,
uncertainty {standard_error {value, method}, confidence_interval {lower, upper,
confidence_level, method}, standard_deviation, num_samples}}` and
`token_usage {input_tokens, output_tokens, total_tokens, input_tokens_cache_read,

Ours (no EEE equivalent): subjects, repeats, stats, comparisons, errors, cost,

**Required:** schema_version, id, bench, question, started_at, revision {repo,
commit}, source_data {dataset_name, version, n_planned, n_completed}, subjects
(each with name plus model_info or harness), repeats {planned, completed},
metric_config, primary_metric, evaluation_results, errors {n, of, counted_as},
cost {usd, basis}, verdict, status. Everything else optional, filled when the
bench has it.

**Who fills what.** `bench-kit stats` owns: `evaluation_results` for metrics
whose `metric_parameters.from` is not `external` (including `subset`), the numbers inside
`comparisons` (diff, uncertainty, wins/ties/losses, sign_test_p), `errors.n`,
`errors.of`, `errors.by_source`, and `token_usage`. Everything else is written
by the run or a human. Metrics with `from: external` (e.g. precision over claims)
are written by the bench's own scorer and carried as is.

**`metric_parameters.from`**
- `score`: mean of `evaluation.score`
- `is_correct`: share of rows with `evaluation.is_correct` true
- `pass_at_k` (with `k`): per task 1 - C(n-c, k) / C(n, k)
- `pass_hat_k` (with `k`): per task C(c, k) / C(n, k) (tau2 pass^k)
- `external`: not computed from samples (default)

**Metric subsets** (optional, bench-kit 0.4.0). Some metrics only make sense on
part of a run's tasks: recall only on tasks that have a known answer, false
alarms only on clean controls. Three optional fields describe that, so
`bench-kit stats` computes the value, interval and paired comparisons over just
those tasks:

```json
"metric_config": {
  "recall": {"metric_name": "Recall on positive tasks", "lower_is_better": false, "score_type": "continuous",
             "min_score": 0, "max_score": 1,
             "metric_parameters": {"from": "score", "missing": "zero"},
             "task_filter": {"field": "metadata.kind", "equals": "positive"}},
  "false_alarm": {"metric_name": "False alarms on clean controls", "lower_is_better": true, "score_type": "continuous",
                  "min_score": 0, "max_score": 1,
                  "metric_parameters": {"from": "score", "field": "metadata.false_alarm", "missing": "excluded"},
                  "task_filter": {"field": "metadata.kind", "equals": "clean"}}
}
```

- `task_filter` (in the metric_config entry, next to `metric_parameters`): which
  tasks count. `{"field": <path>, "equals": <value>}` or `{"field": <path>,
  "in": [<values>]}` keeps tasks whose rows carry that value at the dotted path
  (e.g. `metadata.kind`); `{"sample_ids": [...]}` keeps the listed tasks; both
  together keep tasks that pass both. The match is per task over all its rows
  (every subject and repeat): rows without the value (e.g. errored rows) take
  their task's value from its other rows, a task whose rows disagree is an
  error, and a task with no value at all is left out.
- `metric_parameters.field`: dotted path in each row that holds the per-row
  value, e.g. `metadata.false_alarm`. Default `evaluation.score` (for `score`)
  or `evaluation.is_correct` (for `is_correct`, `pass_at_k`, `pass_hat_k`, where
  the value must be true/false or 0/1).
- `metric_parameters.missing`: what a row with no value counts as: `zero` (0, or
  not correct) or `excluded` (left out). Unset: an errored row follows
  `errors.counted_as` and any other row is left out, as before. With
  `errors.counted_as: excluded` errored rows are dropped first, whatever
  `missing` says.
- `bench-kit stats` writes `subset` into each result of such a metric:
  `{"tasks", "of", "rows_zeroed", "rows_excluded", "filter"}` (this subject's
  kept tasks, its tasks in the run, rows with no value counted as 0, rows with no
  value left out, and the filter in short text). `uncertainty.num_samples` is
  the number of kept tasks with a value. Comparisons on the metric pair only the
  kept tasks. Render prints `(4 of 6 tasks; ...)` next to the number and a
  `Metric subsets` line per run.
- `export-eee` writes the filter into EEE `metric_parameters.task_filter` as its
  short text (EEE parameters are scalars) and adds `n_tasks_in_subset`.
- They apply only to metrics computed from samples (`from` is not `external`).
- These fields need bench-kit 0.4.0 or later: older versions ignore them and
  compute the metric over every task. Pin `aaronjmars/bench-kit@v0.4.0` (or later)
  before writing them.

**Fixed words**
- `status`: complete | partial | failed | invalidated
- `verdict`: SWITCH | KEEP | WINNER:<subject> | NO WINNER | INCONCLUSIVE | SNAPSHOT
  (SNAPSHOT = a measurement with no comparison, e.g. a sentiment snapshot or a single baseline)
- `setup`: standard | custom (custom = anything changed vs the frozen task set
  or default prompts; say what in `setup_notes`)
- `cost.basis`: api | subscription | credit | list-price | none
- `errors.counted_as`: zero | excluded
- `repeats.aggregation`: mean | pass@k | pass^k | best@k | median | olympic
- `source_data.version`: `N-X` (section 6)

**Headline:** `"headline": true` pins a run as the README latest result (newest such run wins).

**Corrections** are appended, never overwrite silently:
`{"date", "author", "reason", "field", "old", "new"}`. A correction that flips
the verdict also sets `status` or adds a new run that sets `superseded_by`.

**Suppressions** for one manifest: `"lint_ignore": [{"rule": "BL007", "reason": "..."}]`.

**Uneven subjects and repeats** (optional). When subjects legitimately have
different task sets (e.g. a different number of items per source) or one run
holds configs with different repeat counts, declare it instead of suppressing
BL004:

```json
"source_data": {"dataset_name": "example-items", "version": "1-A", "n_planned": 40, "n_completed": 40,
                "n_completed_by_subject": {"source-a": 25, "source-b": 15}},
"repeats": {"planned": 3, "completed": 3, "completed_by_subject": {"config-fast": 1}}
```

Subjects not listed use `n_completed` / `repeats.completed`; with per-subject
counts, `n_completed` is the number of distinct tasks across all subjects.
Comparisons pair only the tasks both subjects have: `num_samples` is the number
of shared tasks and `bench-kit stats` writes `"unpaired": {"baseline": k,
"candidate": j}` when either side had tasks the other lacks. Per-task values
still average a subject's own repeats first. BL005 counts the repeats of the
subjects in the comparisons that back the verdict.

**Clustered intervals** (optional): `"stats": {"cluster_by": "date"}`. See
section 7 rule 11.

## 5. Per-task file (`runs/<id>/samples.jsonl`, schema `bench-sample/1`)

One JSON line per task x subject x repeat (EEE instance names where they exist):

```json
{"sample_id": "task-0001", "sample_hash": "sha256:...", "subject": "baseline", "repeat": 1,
 "evaluation": {"score": 3.2, "is_correct": null, "num_turns": null, "tool_calls_count": 12},
 "token_usage": {"input_tokens": 0, "output_tokens": 0, "total_tokens": 0},
 "performance": {"latency_ms": 300000},
 "cost_usd": 0.40,
 "error": null,
 "metadata": {"category": "summarize"}}
```

- `sample_id` is the task id (stable across runs); `repeat` counts from 0 or 1,
  consistently within a run.
- `error` is null or `{"source": "infra|agent|judge|task", "type", "message"}`.
  With `errors.counted_as: zero` an errored row with a null score counts as 0
  (and not correct); with `excluded` it is dropped.
- Row count per subject must equal `n_completed x repeats.completed`, or that
  subject's entries in `source_data.n_completed_by_subject` and
  `repeats.completed_by_subject` when the manifest declares them.
- `cluster` (optional): a cluster label (string or number) used when the
  manifest sets `stats.cluster_by` to `"cluster"`. Same value for every row of a task.
- `output` (optional): the model's answer, used by `export-eee` for
  `interaction_type: single_turn` runs (EEE requires an output object there): a
  string, a list of strings, or `{"raw": [...], "reasoning_trace": [...]}`.
  Rows without it export the minimal valid `{"raw": []}`.
- Keep this file even when transcripts are too big or sensitive to commit.

## 6. METHOD.md headings (benchmark card)

1. Goal and scope: what decision this bench serves; subject type (model, harness, setup, provider).
2. Tasks and data: source, size, how tasks were chosen, solvability check (oracle or reference run).
3. Metrics: how each is computed, unit, higher or lower is better, primary metric.
4. Judge: model, prompt, votes, evidence it agrees with humans or a second judge.
5. Baselines: trivial / do-nothing agent, random, oracle or ceiling where they make sense.
6. Noise band: result of an A/A run (same config twice), date, and harness version it was measured on.
7. Fairness and leak register: what each agent could see (web, git history, ground truth), isolation used, known leaks.
8. Known flaws and their estimated impact.
9. Out of scope: what these numbers must not be used for.
10. Changelog, Keep a Changelog style: `### [2-A] - 2026-10-09` + what changed.

**Task-set version `N-X`** (from inspect_evals): bump N on any change that moves
scores (tasks, scoring, rubric, prompt, judge, bug fix); bump X only for
interface changes. Runs are compared only within the same N; otherwise the
comparison must list what differs (`compared_with`).

## 7. Stats rules (sized for 2-3 runs per arm and small task sets)

1. The unit is the **task**. Average repeats within a task first, then compute
   across tasks. Never treat tasks x repeats as independent samples (clustered
   error can be 3x+ the naive one).
2. A vs B on the same tasks: use **paired per-task differences**. Report diff,
   95% CI, and wins/ties/losses with an exact sign test.
3. CI method by case (what `bench-kit stats` does):
   - per-task values all 0 or 1 (pass/fail, single repeat): Wilson score interval
   - otherwise: Student t interval on task means (n - 1 df)
   - A vs B: t interval on paired per-task differences. (Paired Bayes, which
     Bowyer et al. recommend for small-n pass rates, is not implemented yet;
     read pass/fail comparisons with n < 30 together with W/T/L.)
   - timings (e.g. CI runner benches): median, or olympic mean (drop best and worst) when
     n >= 5; failed jobs count as worst. Computed by the bench, `from: external`.
4. With 2-3 repeats, show `per_repeat` values or the min-max range; do not
   present SD across 2-3 runs as an error bar.
5. Repeats: 3 or more preferred, 2 minimum for any SWITCH or WINNER verdict.
   One repeat = the verdict can only be INCONCLUSIVE, KEEP, NO WINNER or SNAPSHOT.
6. Order expensive runs: smoke (5-10 tasks) -> 1 full run -> all repeats, all
   subjects interleaved together, never one arm first.
7. Pre-register: `decision_rule` and `repeats.planned` are written before the
   run. Every attempted run is kept, including failed ones; no re-running to
   fish for a better set (MLPerf rule).
8. Verdict mapping:
   - SWITCH / WINNER: CI of the diff on the primary metric excludes 0 in the
     winner's favour, the diff beats the noise band and the decision rule's
     minimum effect, and the cost rule holds.
   - KEEP: candidate is worse, or not better.
   - INCONCLUSIVE: anything else, including single runs.
9. Very small task sets (n <= 10): always show W/T/L. 6 of 6 wins is p = 0.03 on
   a sign test; 5 of 6 is not significant.
10. Report cost the same way: per run, per task, and per success.
11. Clustered tasks (optional). When tasks are not independent (several items
    from the same day, author, repo or source move together), set
    `"stats": {"cluster_by": "<key>"}` in the manifest. `"cluster"` reads each
    sample row's `cluster` field; any other value names a key in the row's
    `metadata` (a `metadata.` prefix is accepted), e.g. `date` or `author`. A
    task must sit in exactly one cluster; rows without a value (e.g. errored
    rows) take their task's value from its other rows, and a task with no value
    at all is an error. Then, for every metric and every paired comparison,
    `bench-kit stats` uses the cluster-robust (CR1) standard error over the
    per-task values (or per-task differences):
    `se^2 = G / (G - 1) * sum_g (sum_{i in g} (x_i - mean))^2 / n^2`, with G
    clusters, and a t interval with G - 1 df, clipped to the metric range. Wilson
    is not used when clustered (it assumes independence). Fewer than 2 clusters
    gives no interval. `uncertainty.num_clusters` records G; W/T/L and the sign
    test stay per task. With every task in its own cluster this equals the
    unclustered t interval. Unset `cluster_by` (the default) changes nothing.
12. Metric subsets (optional, section 4). A metric with a `task_filter` is
    computed on the kept tasks only: per-task values, the interval (same rules
    as above, with n = kept tasks that have a value), `per_repeat`, and every
    paired comparison on that metric (W/T/L, sign test and `num_samples` over the
    kept tasks both subjects have). Always read such a metric with its n; a
    filter that keeps 2 tasks gives a very wide interval. Decide the filter
    before the run, like the decision rule (rule 7): it is part of the metric.
13. No zero-width intervals. When every per-task value (or every paired diff)
    is equal, the standard error is 0 and a t interval would be `[x, x]`, which
    reads as perfect certainty even on 2 tasks. `bench-kit stats` then writes no
    `confidence_interval` and no `standard_error`, and sets
    `uncertainty.no_interval_reason` (e.g. `"all 2 paired diffs equal"`). The
    same field names the other no-interval cases: `"1 task"`, `"1 shared task"`,
    `"1 cluster"`, and `"standard error is 0"` (clustered values that cancel
    out). Generated files print `[CI n/a: <reason>]`. A comparison without an
    interval never backs a SWITCH or WINNER (rule 8, BL005): read it with W/T/L
    and the sign test, and add tasks for a real interval. Wilson intervals are
    never zero width and are kept.

## 8. Shared conventions

- Dates and times ISO 8601 UTC. Every Status line carries a date.
- Model ids are exact (dated or snapshot ids), plus provider/route. No bare
  aliases like "latest".
- Subject short form: `harness@version+model` (Harbor style), e.g. `omp@18.3.2+claude-haiku-5-5`.
- Any number quoted outside the repo (tweet, blog, PR) carries run id and date.
- Secrets come from a secret store at run time; never in repo, manifests, samples or logs.
- No em or en dashes anywhere.
- GitHub: description = README one-liner; topic `bench`.

## 9. bench-lint

Lives in `aaronjmars/bench-kit` (public) with the JSON Schemas, the renderer,
the stats code and the linter. Bench repos call it from CI through the
composite action `aaronjmars/bench-kit@<tag>`.

Commands:
- `bench-kit stats`: fills the stats-owned fields from samples.jsonl
- `bench-kit render`: rebuilds README latest block, RESULTS.md, runs/INDEX.md
- `bench-kit lint [--warn-only]`: GitHub `::error file=..::` annotations in CI
- `bench-kit export-eee <run> [--org NAME]`: EEE 0.3.0 aggregate + samples files,
  validated against the vendored EEE schemas

Rules (code, level):
- BL001 error: manifest or samples fail JSON Schema, duplicate run id, or id differs from directory
- BL002 error: required file or README section missing; Status has no date; latest markers missing
- BL003 error: generated files out of date (render would change them)
- BL004 error: samples row count per subject (section 5) or recomputed numbers disagree with the manifest (for metric subsets also `num_samples` and the `subset` counts), or stats cannot be computed (e.g. a task in two clusters, or two values for a `task_filter` field)
- BL005 error: verdict SWITCH/WINNER without a primary-metric comparison whose CI excludes 0 (a missing or zero-width CI does not count), or with repeats < 2
- BL006 error: em or en dash in any markdown file or manifest
- BL007 warn: model id is an alias, or harness version missing without `version_unknown_reason`
- BL008 warn: `revision.dirty` true without a correction note
- BL009 warn: task-set version not in the METHOD.md changelog
- BL010 warn: leftover TODO in docs, or `raw.kept` false without location or reason
- BL011 warn: a stored confidence interval has zero width (lower equals upper), e.g. from an older bench-kit or a hand-written external metric (section 7 rule 13)

Suppress in a markdown file with `<!-- bench-lint: ignore BL0xx <reason> -->`,
in a manifest with `lint_ignore`, or repo-wide in `.bench-lint-ignore`.
Legacy repos start with `--warn-only` and switch to errors once migrated.

## 10. Migrating an existing bench

1. Add the fixed docs (README sections, METHOD.md, NEXT.md) and keep the bench's
   own code, runner and raw-data folders where they are.
2. Backfill one manifest (and samples.jsonl) per past run where the per-task data
   still exists. Numbers must recompute to what the old reports say; any
   difference becomes a `corrections` entry, never a silent change.
3. Where the raw data is gone, write the manifest with `raw.kept: false`, a
   reason, only the numbers that survive, and intervals left null.
4. Move old hand-written result files to `docs/` and link them via `writeup`, so
   nothing is lost; RESULTS.md becomes generated.
5. Add the lint to CI with `--warn-only` first, then switch to errors once the
   repo is clean.
